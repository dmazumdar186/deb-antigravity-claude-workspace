## Goal

Every day, send connection requests to the next 25 unsent people from a consolidated master list, never twice to the same person, and hand the operator one table (first name, name, company, position, LinkedIn ID) by email, once a day at 20:00 Europe/Paris.

## Inputs

- **env:** `LINKEDIN_CONNECT_DIR` (optional; default data dir when `--data-dir` is not passed, `.tmp/linkedin_connect`). No API keys: the browser step uses the operator's own Chrome session.

- **Prospect CSVs** (Apollo exports; any column names work if a profile-URL column exists). They live on the operator's machine in the repo root and campaign subfolders ("Bay Area Recruitment Campaign 13 Oct 26/", "Recruitment City Wise/", "Campaign 24 Sep 26 Wellness/"). **Every run consolidates all of them again** (idempotent), so a new CSV dropped there is picked up with no further action. Files whose name contains `bounce` are email bounces, not people: skip them.
- **Shared state = Google Drive folder `linkedin_connect`** (owner's My Drive; find it with the Drive connector by title). Holds `ledger_<ISO datetime>.csv` snapshots (one per run, full copy) and `aliases.csv`. This is the only cross-machine state; **nothing under `data/linkedin_connect/` is ever committed** (repo is public; path is gitignored). No git credentials are needed in the daily loop.
- **Local working dir** `data/linkedin_connect/` (gitignored): `master.csv` rebuilt from the CSVs, `ledger.csv` synced from Drive, `queue_<date>.csv`, `report_<date>.md`.
- Operator's Chrome logged in to LinkedIn, Claude in Chrome extension connected (Cowork).

## Tools / Scripts

`execution/personal_workflows/linkedin_connect_queue.py` (no LinkedIn access, pure bookkeeping):

| Command | Does |
|---|---|
| `consolidate --in a.csv b.csv ...` | Merge into `master.csv`, slug-normalised, dedupe across files and against `aliases.csv`, fill blanks from later files. Re-runnable; new CSVs just add. |
| `sync --ledger f [--aliases f]` | Union rows from another ledger copy (a Drive snapshot, or a report `.md` with its ```ledger block) into the local ledger. Idempotent, never drops a row. Run it on every Drive snapshot before `plan`. |
| `plan [--limit 25]` | Write today's queue (or reprint the unfinished part). Hard cap 25, weekly soft cap 100 trims the day. Skips anyone with a final status; tops the queue back up after skips; `--shuffle` randomises order, seeded by date. |
| `mark <slug-or-url> --status sent\|skipped\|already_connected\|pending\|withdrawn\|retry [--note] [--canonical <slug>]` | Append to ledger; `--canonical` records the redirected slug in `aliases.csv` so consolidate and mark treat it as the same person. Refuses the 26th `sent` of the day (exit 3). Refuses a second entry for the same slug. |
| `report [--date]` | **One** markdown table of that day's sends (#, first name, name, company, position, LinkedIn ID) and nothing else. This is the whole email body. The ledger block that used to follow it was removed 2026-10-26 (operator order: the email is one table); `sync --ledger` still reads legacy reports. |
| `status` | Counts. |
| `lock acquire\|release\|show` | Run lock; `acquire` exits 4 while a live (<120 min) lock exists. |
| `health [--json]` | Invariant check (exit 1 on breach); must be HEALTHY before any send. |

## Daily procedure (Cowork, `/linkedin-connect`)

0. **Pull state, no git.** `Q="python execution/personal_workflows/linkedin_connect_queue.py --data-dir data/linkedin_connect"`. (a) With the Drive connector, find the folder `linkedin_connect`, download every `ledger_*.csv` and `aliases.csv` into `data/linkedin_connect/drive/`, then `$Q sync --aliases drive/aliases.csv` and `$Q sync --ledger <each snapshot>`. (b) `$Q consolidate --in <every prospect CSV in the repo root and the campaign subfolders, excluding *bounce*>`. If the Drive connector is unavailable, stop: reply one line in the session and send nothing (sending blind risks duplicates; the email carries no ledger).
1. `$Q lock acquire` (exit 4 → stop, another slot is running). `$Q health` (UNHEALTHY → guardrail 2). Then `$Q plan --shuffle` → list of ≤25. If it prints "0 to do", release the lock and stop quietly (a later slot on an already-finished day).
2. For each person in the printed order:
   a. Navigate to `linkedin_url` in the logged-in tab. Wait for the profile to render; read the primary action button.
   b. **Normal case (13 of 14 on the first run): header shows `Follow` / `Message` / `More`, and `Connect` is inside the `More` menu.** Open More → Connect → in the dialog choose **Send without a note**. Confirmation is either the alert "Invitation sent to <First>." or the header button flipping to "Pending, click to withdraw invitation" — both are readable from the accessibility tree; no screenshot needed → `mark <slug> --status sent`.
   c. `Connect` directly in the header → same as (b). `Pending` → `mark --status pending`. `Message` with the 1st-degree badge → `mark --status already_connected`. `Follow` only and no Connect in More → `mark --status skipped --note no_connect_button`.
   c2. Dialog "To verify this member knows you, please enter their email to connect" → Escape, `mark --status skipped --note email_required`, **continue**. This is that member's privacy setting, not an account warning (observed 2026-10-23, dan-dieffenbach-909582a; it cost 10 sends when treated as a stop).
   c3. LinkedIn redirected the URL to a different slug (e.g. `karthik-achari-54b347198` → `karthikachari`) → mark with the queue slug and add `--canonical <new-slug>` so a future export carrying the new slug is recognised as the same person.
   d. Profile 404 / "This page doesn't exist" → `mark --status skipped --note profile_gone`. Page timed out or Connect clicked but no `Pending` seen → `mark --status retry`.
   e. Wait a random **45–120 s** before the next profile (`Bash sleep`). Every ~8 profiles, open the LinkedIn feed or a notifications page once and scroll for a few seconds, then continue.
3. **Stop immediately** and mark nothing further if any of these appear: a captcha or "let's do a quick security check", "you've reached the weekly invitation limit", "we've restricted your account", or two consecutive page-load failures on different profiles. Report the trigger verbatim in the session reply (never in the report email). Do not retry that day. (The email-required dialog is **not** a stop trigger; see 2c2.)
4. Stop at 25 `sent` regardless of how many were skipped; the script enforces it, don't argue with exit 3.
5. `$Q report` → writes `report_<date>.md` (the one table). Upload it to the Drive folder as `report_<date>.md`, replacing any same-day copy. **Slots never email the report.** The cloud task "LinkedIn connect: 20:00 daily report" (20:00 Europe/Paris) downloads today's `report_<date>.md` and emails its body verbatim, subject `LinkedIn connects <date> (<n> sent)`; n = table rows. No report file → no email, one line in the operator's session instead. Skips, retries, counts and problems go in the slot's session reply, never in the file.
6. **Push state, no git.** Upload `ledger.csv` to the Drive folder as `ledger_<YYYY-MM-DDTHHMM>.csv` (text/csv, no conversion) and, if aliases changed, upload a fresh `aliases.csv` after trashing the old one. Trash ledger snapshots older than the newest 7. Drive is the only state transport. If the upload fails, say so in the session reply; the next slot retries, and the 20:00 Europe/Paris task reports a day with no snapshot.
7. `$Q status` → one line to the operator: remaining count and days left at 25/day. `$Q lock release`. No commit, no push.

## Output contract — the operator sees one table (operator order 2026-10-26)

The only artefact the operator asked for is a table: first name, name, company, position, LinkedIn ID, emailed once a day at 20:00 Europe/Paris (operator order 2026-10-26). The email body is exactly `$Q report` stdout. No heading, no "25 sent", no skipped/profile_gone notes, no CSV, no status line, no commentary. Anything operational goes in the slot's session reply. Machine state (the ledger) travels only through the Drive snapshot. On 2026-10-25 the email carried a ```ledger CSV block plus a free-text status paragraph; the operator could not read it. Root cause: the v2 audit (2026-10-23) bolted a transport mechanism onto a human deliverable because it was convenient for a Drive-outage fallback, and the runbook's "one line to the operator" got folded into the email. Rule now: human deliverables and machine state never share a channel; a deliverable's columns and shape are a contract, and any new field needs the operator's word.

## Scheduling — three slots, "runs when I log in"

The browser step can only happen while the operator's PC is awake and Chrome is logged in. The schedule is **three device-bound Claude cloud scheduled tasks**, named `LinkedIn connect slot HH:00`, at **08:00, 12:00 and 18:00 Europe/Paris** (operator order 2026-10-26, replacing eight two-hourly slots that burned the usage pool: five of the 2026-10-25 runs died on `USAGE_LIMIT_REACHED`), prompt = the plugin runbook, permission mode auto, Drive + Gmail connectors attached. Every run is idempotent: the first slot after login does the day's work; later slots sync state, see `0 to do`, and exit in under a minute. If the operator changes time zone for a long stay, shift the three cron expressions once. Slot tasks show `folders_state NONE`: the first fire may ask the operator to approve the repo folder once. Prompt changes on a device-bound task go through `update_trigger` from a chat linked to that laptop (the laptop re-signs the prompt; one call per slot); schedule and enable changes do not need the device. The slot model is also device-signed: `update_trigger` with `model` from a cloud session fails (`model cannot be patched directly on a device-bound routine`, observed 2026-10-27); change it from a Cowork chat linked to the laptop, same as a prompt edit. The slots carry no LLM call of their own (the queue script is deterministic), so a cheaper tier only changes the browser-driving session, not the schedule, caps or ledger. Never delete-and-recreate a slot: run history and the device binding go with it, and a run in flight on a deleted task leaves no record (observed 2026-10-26).

## Edge cases / learnings

- Slugs are case-insensitive; the script lowercases. Numeric-suffixed slugs (`john-smith-1a2b3c`) are distinct people, keep them.
- Rows without a LinkedIn URL are dropped at consolidate time and counted in the summary; the operator gets that count, not a silent drop.
- A `sent` the browser could not confirm as `Pending`, or a profile that failed to load, is marked `retry` (non-terminal: out of today's queue, eligible from tomorrow). `skipped` is final.
- Columns are picked by content: the column whose values contain `linkedin.com/in/` wins, so Apollo exports with a separate `Company Linkedin` column and a `Company Website` column resolve correctly. `/company/`, `/pub/` and Sales Navigator URLs are not connectable and are counted as "no URL".
- Dataset: 2026-10-23 morning, 15 Apollo CSVs → 4,959 people; afternoon, 19 CSVs on the operator's machine → **8,202 people** (8,955 cross-file duplicates merged, 6 rows without a profile URL). ~327 days at 25/day. Profile 404 → `skipped --note profile_gone` (seen once, danny-z-19738517).
- Eval set: `execution/personal_workflows/tests/linkedin_connect_eval.py --data data/linkedin_connect/master.csv` (24 cases, deterministic table; results in `docs/reference/linkedin_connect/`). Run after any script change.
- **Browser hygiene (2026-10-23 run):** the Chrome renderer froze once (navigate and screenshot timed out, `find` still worked). Fix: open a new tab, close the frozen one, re-navigate; no double send resulted. The tab-group id can change mid-run ("not in Claude's tab group") → re-run the tabs-context tool. Gaps used were 59–119 s with one feed detour after profile 8.
- **Why Drive, not git (2026-10-23):** the repo is public (the first dataset commit exposed the prospect list; removed from HEAD the same day; operator chose to keep the repo public and not rewrite history) and the device shell has no GitHub credential. The daily loop touches git only to read the script. Code ships via `git pull` on the operator's machine.
- **Dirty local checkout (observed 2026-10-23: local main 392 commits behind, 12 modified tracked files, ~164 untracked files that also exist upstream, git on the OneDrive checkout takes >160 s per command):** at the start of a run, `git fetch origin main`; if `git merge --ff-only origin/main` refuses, run `git stash push -u -m "linkedin-connect auto-stash <date>"` then the merge again. The stash is reversible and never dropped by the routine; the operator can inspect it with `git stash list`. Never `reset --hard`. Remove stale `.git/index.lock` / `ORIG_HEAD.lock` first when no git process is running. If even that fails, read the current script with `git show origin/main:execution/personal_workflows/linkedin_connect_queue.py > execution/personal_workflows/linkedin_connect_queue.py` and the skill/runbook the same way, and continue.
- **Cloud report task** ("LinkedIn connect: 20:00 daily report", daily 20:00 Europe/Paris, cloud session with Drive + Gmail): downloads today's `report_<date>.md` from the Drive folder and emails its body verbatim to the operator (idempotent: skips if a `LinkedIn connects <date>` email was already sent today); no report file → checks for a HEALTH FAIL email and otherwise posts one line saying the PC never ran. It never rebuilds state from email, never writes to Drive and never touches LinkedIn. Prompt text is the trigger itself (not in the repo); update it with `update_trigger` when this section changes.
- The repo lives inside OneDrive on the operator's machine, which produces stale `.git/index.lock` files. Removing that file when no git process is running is safe and expected.
- Cloud session cannot run steps 2–3. If asked there, run `plan`/`report` and tell the operator to finish in Cowork.
