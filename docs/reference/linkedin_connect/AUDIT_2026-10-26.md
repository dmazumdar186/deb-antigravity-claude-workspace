# LinkedIn connect — system audit and eval, 2026-10-26

Trigger: the operator received the 2026-10-25 report email and could not read it. Asked for one table (first name, name, company, position, LinkedIn ID); received a title, a count line, the table, a 26-row CSV ```ledger block and a free-text status paragraph. ## 1. What slipped and why

| # | Defect | Where it came from | Why it was not caught |
|---|---|---|---|
| D1 | ```ledger CSV block in the email | v2 audit 2026-10-23 (V3 "Drive unavailable" fallback): the report file was reused as a state-transport so the ledger could be rebuilt from the inbox | The eval (c16) only checked the table rows; it never asserted "nothing else". The directive's contract line was rewritten to describe the new output instead of being treated as fixed. |
| D2 | Status paragraph ("this slot found…", "8122 remaining") | Runbook step 6 "one line to the operator" was ambiguous about channel; the slot agent folded it into the email | No instruction said "email body = table only"; nothing in the eval covers agent prose |
| D3 | Eight slots/day burning the usage pool | v2 audit V1: "unpredictable login hour" solved by slot density instead of by asking the operator | Schedule chosen by the auditor, never confirmed with the operator; five of 2026-10-25's runs died on `USAGE_LIMIT_REACHED` |

Pattern across projects: during a *hardening* pass, a convenient mechanism (a fallback transport, a denser schedule) gets attached to a human-facing artefact because the same file or task is already there. The product contract is not written down as a test, so the diff looks like an improvement. The rule promoted to CLAUDE.md principle 7: a deliverable's fields, shape, channel and cadence are a contract; machine state gets its own channel; changing either needs the operator's word, and an audit is not that word.

## 4. Five-lens eval with KPIs

Scores 1–5. Technical KPI = measurable from source/logs; behavioural KPI = what the operator experiences.

Measured from source and from the 2026-10-25 run, not from the docs. "Before" = state the operator saw on 2026-10-25; "Now" = commit ecd6729 + the trigger changes made today.

### 4.1 Architecture — 4/5 (was 2/5)
Three layers hold: directive (SOP), orchestration (slot agent + 20:00 cloud task), execution (`linkedin_connect_queue.py`, 495 lines, 8 subcommands, no LinkedIn access). The defect was a layer leak: execution emitted a transport payload into the human deliverable, and the auditor changed the contract. Now the human artefact (`report_<date>.md`) and machine state (`ledger_*.csv`) are separate files with separate consumers.
- Technical KPI: channels shared between a human deliverable and machine state. Before 1 (email). Now 0. Target 0.
- Behavioural KPI: operator questions per report email ("what is this?"). Before 1 email → 1 complaint. Target 0; measure over the next 7 emails.
- Open: slot-task prompts live only in the trigger, not in git; the runbook file in `.claude/plugins/` is the source of truth and a prompt change needs one `update_trigger` per slot from a device-linked chat (done 2026-10-26 09:38). Deduct 1 until the propagation is scripted.

### 4.2 Data — 4/5 (was 3/5)
Ledger is append-only; `sync` unions and never deletes; `TERMINAL = STATUSES − {retry}` prevents re-queuing; aliases map redirected slugs. Loss path removed by this change: the email was a second copy of the ledger. Remaining loss path: Drive upload fails at the 18:00 slot and the laptop sleeps → the day's rows exist only on the laptop until the next slot syncs them. The 20:00 task now names that case explicitly.
- Technical KPI: ledger rows recoverable from Drive within 24 h of marking. Measured 2026-10-23: 100% (snapshot rebuilt the local dir byte-identically). Target 100%.
- Behavioural KPI: duplicate connection requests to one person. Before 0 (health invariant `no_double_terminal_rows`). Target 0.

### 4.3 Data structures — 5/5
Flat CSVs with fixed field orders (`LEDGER_FIELDS` = ts,date,slug,name,status,note); slug is the primary key everywhere; status is a closed enum (6 values) validated by `health` (`ledger_statuses_valid`). Report cells are now sanitised (`_cell`: whitespace collapse, pipe escape), closing the one structural hole QA found (a `|` in a company name split the row).
- Technical KPI: malformed table rows per report. Before: 1 per pipe-bearing field. Now 0 (eval c25). Target 0.
- Behavioural KPI: the operator can click every LinkedIn ID in the table. Measured 25/25 on the 2026-10-25 email. Target 100%.

### 4.4 System design — 4/5 (was 2/5)
Idempotent slots + run lock (`LOCK_TTL_MIN` 120) + health gate (10 invariants) are sound. The 8-slot schedule was the failure: five of eight runs on 2026-10-25 ended `USAGE_LIMIT_REACHED`, so the density bought nothing and starved the pool. Three slots now; the report email is one cloud task at 20:00 with an "already emailed" guard. Trade-off accepted: a login after 18:00 Europe/Paris sends nothing that day.
- Technical KPI: slot runs per day. Before 8 (+1 check). Now 3 (+1 report). Target ≤4. Failed runs per day due to usage limit: before 5, target 0; verify on 2026-10-27.
- Behavioural KPI: report emails per day. Before 1–2 (a second slot could re-send). Now exactly 1 at 20:00, or a one-line notification if the PC never ran. Target 1.

### 4.5 Algorithm — 5/5
`plan --shuffle` is seeded by date (eval c18: deterministic across runs); the daily cap is enforced at `mark` time (exit 3), not only at planning; the weekly soft cap trims the batch (`room = 100 − week`). Nothing here changed today.
- Technical KPI: cap breaches. Measured 0 in 3 live days (75 sends / 7 days, max 25/day). Target 0.
- Behavioural KPI: days the operator had to intervene in sending. 0 of 3. Target 0.
