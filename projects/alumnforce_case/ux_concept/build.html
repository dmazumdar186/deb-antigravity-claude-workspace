Nine steps

1Shared clean-up lists

WhatCollect every distinct raw value per field across schools, with member counts (read-only). Match cities via the segmenter's existing map lookup (canonical city + map point + country), countries via a fixed variant list, sector via the NAF industry code already on the current job, else a company list. People review the most frequent values first; rare ones stay suggested.
Where it runsMariaDB tables: city, country, employer→sector, plus a per-school override table (school, field, raw value → cleaned value, who, when).
Why this wayOne shared list serves every school. The override wins, so each school keeps the last word on its own data. A mapping confirmed by several schools is promoted to the shared list (Annex D), so the lists grow from schools' own confirmations.

2Cleaned columns next to the originals

Whatcity_norm, country_norm, sector_norm + status.
Where it runsMariaDB, beside the original profile fields.
Why this wayOriginals are never touched. The member's own entry stays exactly as typed.

3Filling the columns

WhatA small step in every profile save, plus a one-time backfill.
Where it runsSymfony: inside the profile save; the backfill runs in batches.
Why this wayNew entries are clean from day one. The backfill is safe to re-run and writes only on change.

4Reliability label

WhatComputes Current To confirm To reactivate from per-school thresholds into one column. Future dates are treated as unknown.
Where it runsA nightly job. The two dates are already recorded by the platform: the exercise export contains date_maj_profil and derniere_connexion.
Why this wayNightly because time passes: a label changes even when nobody edits the profile.

5OpenSearch

WhatSix new fields per school index.
Where it runsRebuilt as a copy, switched over only after checks (same member count, spot checks). Test schools first, then waves.
Why this wayNobody searches a half-built index. Afterwards, nightly partial updates only for members whose label changed.

6Segmenter

WhatWith reliability on, the City filter reads city_norm: pick London once, see what was grouped. Two new date filters. Three label counts. With it off, the segmenter is exactly as today.
Where it runsVue.js segmenter. The date filters reuse the existing date filter type; the three counts come from the same search.
Why this wayExisting building blocks, no extra search.

7Admin review screen

WhatShows suggested values only; the admin confirms or changes them.
Where it runsBack-office → override table → background recompute → search index update.
Why this wayLogged, undoable, and applies to that school only.

8Switches

WhatCleaned columns are filled in the background for all schools, unseen. The cleaned filters, the review screen and the labels appear only when the school switches reliability on. With it off, the segmenter is exactly as today.
Where it runsSchool settings.
Why this wayConsistent spelling infers nothing about a person. A reliability label is derived personal data, so the school decides. And the brief requires the segmenter to stay identical when the feature is off.

9Checks per school

What
  • Member counts equal before and after the rebuild.
  • No raw field changed (fingerprint before and after).
  • Before/after on a known question: the brief's own sentence returns 2 on raw values and 26 with clean city and sector (Annex B).

Once, before launch (weeks 1–2): CS hand-checks 100 members on two schools; the 2/4-year cut-offs ship only if they agree at least 80% of the time.

Where it runsAt each school's switch-over.
Why this wayEach school goes live on evidence.

The scrubber: what leaves the platform

  1. Flag and quota check; length cap.
  2. Remove e-mails and phone numbers.
  3. Remove exact full-name matches (first + last token) against this school's member table.
  4. Replace any other capitalised two-word sequence with a placeholder the admin sees (e.g. {{P1}}); the validator re-substitutes it locally.
  5. Keep place and sector words (allow-listed).
  6. Log every hit, never block (surnames like Paris, Martin or Finance would block constantly); then cache lookup.

Example A (fictional): "Diplômés 2015–2018 qui travaillent chez Goldman Sachs à Londres, contact : prenom.nom@example.com" → "Diplômés 2015–2018 qui travaillent chez {{P1}} à Londres, contact : [removed]"

Sent: the scrubbed question, filter (criterion) and operator names, closed list values (sectors, countries, degree types), school-defined filters as typed ids (e.g. "custom_12: amount"). Never sent: member fields, employer lists.

"Only the administrator's question, scrubbed of identifiers and full names, and the names of the filters leave the platform, to a model hosted in the EU under a no-retention, no-training contract. No member profile is ever sent; residual hits in the question are logged and reviewed." (DPO sentence, slide 9)
MeasuredFalse-flag rate on the eval set.
Where it runsPre-flight, in AlumnForce's code, before the AI gateway.
